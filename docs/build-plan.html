1. Approach & guiding principles

The roadmap specified five build phases across four systems (React frontend, Spring Boot backend, Python/FastAPI AI service, Postgres+pgvector). Rather than writing code phase-by-phase and hoping it worked, each phase was closed out with a real, running verification before moving to the next — the goal was a provably working MVP, not just code that compiles.

  • Mock-LLM mode from day one: the AI service was built with a deterministic mock mode (rule-based embeddings, canned plans, known-good patches) so the entire pipeline — RAG, planning, coding, testing, retrying, PR creation — could be exercised end-to-end without any Gemini or GitHub API key.
  • A disposable, buggy test subject: rather than testing against a real GitHub repo, a small dummy Spring Boot service (user-service) was seeded with 5 intentional, realistic bugs, each with a failing test. This turned "does the agent work?" into a falsifiable question with a red/green answer.
  • Verify after every phase: each phase ends with actually starting the service(s) and hitting real endpoints/UI, not just a successful build.
  • Git isolation: the project got its own nested git repo (never touching the user's home-directory-level repo), and the dummy buggy service got a second, independent repo, since the agent needs to create branches and commits against it.

4. Phase 2 — RAG system

PHASE 2
  • rag/indexer.py — walks a repo's Java files, chunks them (line-window with overlap), embeds each chunk, stores/replaces them in code_embeddings keyed by repo_id.
  • rag/retriever.py — cosine-distance nearest-neighbor search via pgvector's <-> operator.
  • llm.py — the mock/real embedding switch: mock mode uses a deterministic feature-hashing bag-of-words embedding (not semantically trained, but lexically meaningful — chunks sharing vocabulary with the query rank closer), so retrieval quality is genuinely exercised without an API key.

Verified: indexed the real dummy repo, queried for "NullPointerException email domain", and confirmed pgvector returned the actual files containing that bug, ranked first — checked directly against the code_embeddings table in Postgres, not just the API response.

5. Phase 3 — AI agents (FastAPI + LangGraph)

PHASE 3
Agent / moduleResponsibility

Verified: called /analyze directly against the real dummy repo and got back a real plan + real ranked relevant files. This is also where a LangGraph API bug was caught early (a node returning an empty dict violates LangGraph's "must write at least one key" contract) — fixed before it reached the integration phase.

6. Phase 4 — Testing & self-correction loop

PHASE 4

This phase needed something to actually test against, so a companion deliverable was built first:

4a. Dummy user-service — 5 intentional bugs

#BugLocation
1NullPointerException on unknown email lookupUserService.getEmailDomain
2Returns 200 instead of 404 for missing userUserController.getUser
3Accepts null/blank email with no validationUserService.createUser
4Discount subtracts raw percent instead of scaling pricePricingService.calculateDiscountedPrice
5Unhandled DB exception leaks out of the service layerUserService.updateUserEmail

Each bug shipped with a corresponding JUnit test designed to fail against the buggy code, plus a markdown issue file describing it (mirroring a real GitHub issue).

Verified: ran mvn test against this repo before touching the agent — confirmed exactly 6 tests failed across all 5 bug categories (issue #5 needed two assertions). This "red baseline" is what makes the self-correction loop provable rather than assumed.

4b. Self-correction loop

Root-cause fix mid-build: the first end-to-end run of the loop against issue #1 failed — not because the fix was wrong, but because mvn test runs the whole suite, so fixing bug #1 still left tests red for bugs #2–5. Fixed by scoping each ticket's test run to only the test(s) relevant to that issue (bug_catalog.py's test_filter_for), mirroring how a real agent should not be blocked by unrelated pre-existing failures.

Verified: ran /implement against all 5 issues independently. Each one: applied its patch, ran its scoped tests, passed in 1 attempt, committed to its own fix/issue-N branch off a clean main. Confirmed via git diff that each patch was minimal and correct (e.g. issue #4's diff was exactly the one-line formula fix). Confirmed main remained untouched and still red throughout.

7. Phase 5 — Integration & end-to-end verification

FINAL

With all three services individually proven, the last step was proving they work together, driven entirely through the real backend API (not by calling the AI service directly):

  1. Registered QA + Developer users, connected the dummy repo, created a ticket for issue #2, assigned it.
  2. Triggered Analyze via the backend → confirmed live SSE events streamed in real time, plan landed on the ticket, status reached PLAN_READY.
  3. Triggered Approve → confirmed status walked through PLAN_APPROVED → IMPLEMENTING → TESTING → PR_CREATED, with a real diff and real mvn test output attached to the ticket's step timeline.

This full-stack run surfaced two integration-only bugs invisible from any single service in isolation — see below.

8. Bugs found and fixed during verification

1. Async Hibernate lazy-load crash. AgentService's @Async methods loaded a Ticket by ID, then accessed its lazy repo association from a thread with no active Hibernate session → LazyInitializationException. Fixed with a JOIN FETCH query (TicketRepository.findByIdWithRepo).
2. JDK HttpClient vs. uvicorn. Spring's RestClient, backed by Java's HttpClient, sends an Upgrade: h2c cleartext-HTTP/2 negotiation header by default. uvicorn didn't understand it and silently dropped the request body — every backend→AI-service call arrived as an empty body, surfacing as a confusing 422 Field required from FastAPI. Diagnosed by capturing the raw TCP request with nc. Fixed by forcing HttpClient.Version.HTTP_1_1 in AgentClient.

Both were only discoverable by running the actual full-stack loop — neither was visible from reading the code or from any single service's unit tests.
